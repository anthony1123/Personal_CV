# QM Bug Ticket 智能分析系统 PRD

## 1. 文档信息

- 产品名称：QM Bug Ticket 智能分析系统
- 产品定位：面向研发团队的 B 端内部提效系统
- 当前形态：个人 Agent 工作流验证
- MVP 形态：团队内可复用的 Bug Ticket 分析工具
- 未来形态：面向需求迁移和实现迁移的 Agent 工作流能力
- 目标用户：产品经理、研发工程师、QA/QM 测试工程师、技术负责人
- 文档版本：V0.2

## 2. 产品定义

该系统面向项目需求实现阶段已经完成、QM 测试开始产出 bug ticket 的场景，自动结合 Jira bug issue、Jira REQ/Epic、Confluence 文档库和 GitLab 代码库，完成问题归属、需求关联、代码实现定位、影响范围分析和修复工时初评，并生成结构化分析报告，辅助 PO、RD、QA/QM 更快完成 bug 初筛和处理决策。

一句话定义：

面向 QM 测试阶段 bug ticket 的 Agent 分析工作流系统，用多源上下文检索和结构化推理降低团队 bug 分析成本。

## 3. 背景与问题

在项目进入 QM 测试阶段后，测试团队会持续提交 bug ticket。PO、RD 和 QA/QM 需要围绕每个 bug 完成一系列判断：

- 该 bug 是否与本组负责功能相关
- bug 对应哪个 REQ、Epic 或业务需求
- 正确业务行为应该是什么
- 当前代码中相关功能是如何实现的
- 修复可能影响哪些模块、接口或业务流程
- 修复改动量和工时大致是多少
- 是否需要跨团队确认、需求澄清或重新排期

当前这些判断依赖人工在多个系统之间切换：

- Jira bug ticket：查看问题描述、复现步骤、严重级别、评论和状态
- Jira REQ/Epic：查找原始需求、验收标准和需求拆解
- Confluence：查找业务规则、流程说明、接口说明和历史决策
- GitLab：查找代码实现、模块结构、提交记录和潜在改动点

主要问题：

- 上下文分散，单个 bug 的分析链路长
- 需求定义、文档说明和代码实现之间缺少自动关联
- PO、RD、QA/QM 对同一 bug 的判断口径容易不一致
- 新成员或跨模块问题处理成本高
- 分析结论没有结构化沉淀，类似问题重复消耗时间

当前个人已基于 Jira MCP 与 Claude Code 搭建轻量工作流，能够针对 bug ticket 生成固定格式分析报告。个人实测每天约处理 5 个 issue，单个 issue 节省约 1-2 小时人工分析时间。

## 4. 产品目标

### 4.1 MVP 目标

MVP 阶段聚焦 QM 测试阶段 bug ticket 分析，不做通用 Jira 处理平台。

核心目标：

- 将 bug 初步分析流程标准化
- 自动关联 bug ticket、REQ/Epic、Confluence 文档和 GitLab 代码上下文
- 生成可供 PO、RD、QA/QM 协作确认的结构化分析报告
- 降低单个 bug 的人工检索和初步判断成本
- 验证该 Agent 工作流是否具备团队内复用价值

### 4.2 非目标

MVP 阶段不解决以下问题：

- 不自动修复代码
- 不自动关闭或流转 Jira 状态
- 不替代 RD 的最终技术判断
- 不替代 QA/QM 的最终测试结论
- 不做完整低代码 Agent 工作流平台
- 不覆盖所有类型 Jira issue
- 不处理未来项目迁移的完整链路

## 5. 当前场景与未来场景

### 5.1 当前 MVP 场景

当前项目处于需求实现完成后的 QM 测试阶段，系统重点处理 QM 测试产生的 bug ticket。

典型场景：

1. QM 提交 bug ticket
2. PO 或 RD 触发智能分析
3. 系统读取 bug 描述、复现步骤、严重级别和评论
4. 系统检索相关 REQ/Epic、Confluence 文档和 GitLab 代码
5. 系统生成 bug 分析报告
6. PO、RD、QA/QM 对报告进行确认或修正
7. 团队基于报告决定修复方案、工时和后续处理动作

### 5.2 未来扩展场景

未来可扩展到项目需求定义与实现功能迁移场景。

扩展方向：

- 从旧项目 REQ/Epic 中抽取需求定义
- 从 Confluence 中抽取业务规则和流程说明
- 从 GitLab 中识别已有功能实现
- 辅助新项目进行需求重建、功能迁移和影响分析

该方向仅作为 Roadmap，不纳入 MVP 范围。

## 6. 用户角色与职责

### 6.1 产品经理

职责：

- 判断 bug 是否符合原始需求定义
- 确认 bug 是否属于本组功能范围
- 判断是否需要需求澄清、范围调整或跨团队沟通
- 确认最终处理建议

关注内容：

- 相关 REQ/Epic
- 业务规则依据
- 影响范围
- 是否需要重新排期

### 6.2 研发工程师

职责：

- 确认代码实现定位是否准确
- 判断修复方案和改动范围
- 评估技术风险和修复工时
- 补充最终技术结论

关注内容：

- 相关 GitLab 模块
- 代码实现逻辑
- 潜在改动点
- 技术风险和工时

### 6.3 QA/QM 测试工程师

职责：

- 提供 bug 复现信息
- 确认问题现象是否被正确理解
- 判断测试影响范围
- 补充验证场景和回归范围

关注内容：

- bug 现象
- 复现步骤
- 测试环境
- 验证范围

### 6.4 技术负责人 / Admin

职责：

- 维护数据源接入
- 配置团队分析模板
- 管理基础权限边界
- 复盘分析质量和系统指标

关注内容：

- 数据源覆盖度
- 报告准确率
- 团队使用情况
- 权限和信息安全

## 7. 数据源与用途

| 数据源 | 输入内容 | 用来判断什么 | 输出到报告哪里 |
|---|---|---|---|
| Jira Bug Ticket | 标题、描述、复现步骤、严重级别、优先级、评论、附件、状态 | 问题现象、影响范围、处理优先级 | Bug 概述、问题分析、影响范围 |
| Jira REQ/Epic | 原始需求、验收标准、需求拆解、关联 issue | bug 对应的需求定义和验收标准 | 相关需求定义、需求符合性判断 |
| Confluence | 业务规则、流程说明、接口说明、历史决策、FAQ | 正确行为、边界规则、业务约束 | 业务依据、风险点、待确认问题 |
| GitLab | 代码文件、模块结构、提交记录、分支信息、配置文件 | 代码实现逻辑、潜在改动点、技术影响范围 | 代码实现、改动量、工时评估 |

## 8. 核心业务流程

| 流程节点 | 触发条件 | 参与角色 | Agent 做什么 | 人工确认什么 | 输出 |
|---|---|---|---|---|---|
| Bug 输入 | 用户输入或选择 Jira bug ticket | PO / RD / QA | 读取 bug 基础信息 | 确认 ticket 是否需要分析 | 分析任务 |
| 问题理解 | bug 信息读取完成 | Agent / QA | 总结问题现象、复现条件和异常表现 | QA 确认问题理解是否准确 | 问题概述 |
| 归属判断 | 问题理解完成 | Agent / PO | 判断是否与本组功能相关 | PO 确认归属和优先级 | 相关性结论 |
| 需求关联 | 归属可能相关 | Agent / PO | 检索相关 REQ/Epic 和 Confluence 文档 | PO 确认需求依据是否有效 | 需求关联结果 |
| 代码定位 | 需求关联完成 | Agent / RD | 检索 GitLab 相关模块和实现逻辑 | RD 确认代码定位是否准确 | 代码实现摘要 |
| 影响分析 | 代码定位完成 | Agent / RD / QA | 分析改动量、风险点和测试范围 | RD/QA 确认技术和测试影响 | 影响评估 |
| 工时初评 | 影响分析完成 | Agent / RD | 基于改动范围和历史类似问题估算工时 | RD 确认或修正工时 | 工时区间 |
| 报告生成 | 分析完成 | Agent | 生成固定格式分析报告 | PO/RD/QA 确认报告结论 | Bug 分析报告 |
| 反馈沉淀 | 报告被使用后 | PO / RD / QA | 记录修改点和采纳情况 | 用户标记报告质量 | 反馈记录 |

## 9. MVP 功能范围

### 9.1 Bug Ticket 输入与读取

支持用户输入 Jira bug ticket key，系统自动读取 ticket 信息。

读取字段：

- Issue key
- 标题
- 描述
- 复现步骤
- 严重级别
- 优先级
- 状态
- 创建人
- 负责人
- 所属项目
- 关联 REQ/Epic
- 评论
- 附件链接

验收标准：

- 能读取指定 bug ticket 的核心字段
- 无权限或 ticket 不存在时给出明确失败原因
- 读取结果可进入后续分析工作流

### 9.2 多源上下文检索

系统基于 bug ticket 信息检索相关上下文。

检索来源：

- Jira REQ/Epic
- 历史 bug ticket
- Confluence 文档
- GitLab 代码库

检索策略：

- 基于关键词匹配识别功能模块
- 基于 Jira 关联关系查找 REQ/Epic
- 基于需求编号、模块名、接口名检索 Confluence
- 基于模块名、类名、接口名、配置项检索 GitLab

验收标准：

- 每类可用数据源都应返回候选结果
- 每条候选结果必须说明匹配依据
- 系统必须区分“明确关联”和“推测相关”
- 当数据源为空或无权限时，报告中必须明确说明

### 9.3 需求符合性分析

系统应判断 bug 现象与原始需求定义、验收标准或业务规则之间的关系。

输出内容：

- 相关 REQ/Epic
- 相关验收标准
- Confluence 业务规则依据
- bug 是否偏离预期行为
- 是否存在需求定义不清或冲突

验收标准：

- 结论必须附带来源
- 对需求不明确的问题必须标记为“需 PO 确认”
- 不允许在缺少依据时直接断言需求结论

### 9.4 代码实现定位

系统应根据需求关联结果和 bug 描述，定位 GitLab 中可能相关的代码实现。

输出内容：

- 相关代码仓库
- 相关模块或服务
- 相关文件路径
- 实现逻辑摘要
- 可能改动点
- 不确定点

验收标准：

- 必须标记代码定位的置信度
- 必须区分明确命中的文件和推测相关的文件
- 对低置信度代码判断必须提示 RD 确认

### 9.5 影响范围与风险分析

系统应基于需求和代码上下文分析 bug 修复可能产生的影响。

输出内容：

- 影响业务流程
- 影响功能模块
- 影响接口或数据结构
- 可能影响的测试范围
- 技术风险点
- 跨团队依赖

验收标准：

- 风险结论必须说明依据
- 测试范围应能被 QA/QM 继续补充
- 跨团队依赖不确定时必须标记待确认

### 9.6 改动量与工时初评

系统应给出修复改动量和工时区间。

输出内容：

- 改动量：小 / 中 / 大
- 工时预估：例如 0.5-1 天、1-2 天、2-3 天
- 估算依据
- 主要不确定因素

验收标准：

- 工时必须用区间表达
- 必须展示估算依据
- 工时结论必须由 RD 最终确认
- 不允许输出无依据的确定工时

### 9.7 结构化分析报告

系统应生成固定格式报告，供团队协作处理。

报告模板：

```markdown

### 3. 与本组功能的相关性
- 结论：

- 置信度：

### 4. 相关需求定义
- 相关 REQ/Epic：
- 验收标准：
- Confluence 依据：
- 需求符合性判断：
- 需 PO 确认项：

### 5. 代码中的需求实现
- 相关仓库：
- 相关模块：
```

验收标准：

- 每次分析必须使用固定模板
- 字段为空时必须说明原因
- 关键结论必须能追溯到 Jira、Confluence 或 GitLab 来源
- 报告应支持复制到 Jira 评论或团队协作工具

### 9.8 人工确认与反馈

用户可以对报告结果进行确认和反馈。

反馈动作：

- 确认可用
- 少量修改后可用
- 大量修改后可用
- 不可用
- 标记上下文无关
- 修正工时
- 修正代码模块
- 修正需求关联

记录字段：

- 被修改字段
- 修改原因
- 最终采用结论
- 实际处理工时
- 实际节省时间

验收标准：

- 每份报告都可以记录反馈
- 反馈可以按字段统计
- MVP 阶段反馈数据用于人工复盘，不要求自动训练模型

## 10. 权限与角色边界

MVP 阶段不优先建设复杂 RBAC，但必须遵守现有系统权限边界。

基础原则：

- 用户只能分析自己已有权限访问的 Jira ticket、Confluence 文档和 GitLab 仓库
- 系统不绕过 Jira、Confluence、GitLab 的原有权限体系
- 报告中不得暴露用户无权限访问的内容
- 不同角色可以对报告中不同字段进行确认或修正

初始角色边界：

| 角色 | 可查看 | 可确认/修改 | 不应拥有 |
|---|---|---|---|
| PO | Bug 信息、需求关联、业务影响、处理建议 | 归属判断、需求符合性、优先级、处理建议 | 直接确认代码改动结论 |
| RD | Bug 信息、代码实现、影响范围、工时 | 代码定位、改动量、技术风险、工时 | 修改原始需求定义 |
| QA/QM | Bug 信息、问题现象、测试影响范围 | 复现信息、测试范围、验证建议 | 确认最终技术方案 |
| Admin | 数据源配置、模板配置、使用指标 | 数据源、模板、权限边界 | 直接替代业务和技术判断 |

后续若团队使用规模扩大，再建设完整 RBAC。

## 11. 非功能需求

### 11.1 准确性

- 系统必须区分事实、推测和待确认事项
- 关键结论必须给出来源或依据
- 低置信度结论必须提示人工确认
- 不允许把模型推测包装成确定事实

### 11.2 可追溯性

- 相关 REQ/Epic 应附带编号或链接
- Confluence 依据应附带页面标题或链接
- GitLab 代码依据应附带仓库、模块或文件路径
- 工时估算应附带判断依据

### 11.3 稳定性

- 单个 bug 分析失败时不影响其他 bug
- 数据源不可用时应明确标记失败来源
- 报告生成失败时保留已完成的中间分析结果

### 11.4 性能

MVP 阶段目标：

- 单个 bug ticket 分析时间控制在 3 分钟以内
- 常规 bug 报告生成成功率不低于 90%
- 多源检索失败时能降级输出部分报告

### 11.5 安全

- 不存储用户无权限访问的数据
- 不将代码、需求或文档内容发送到未授权环境
- 报告中涉及敏感信息时应保留原系统权限链接，而不是复制完整内容

## 12. 关键指标

### 12.1 效率指标

- 单个 bug 平均人工分析耗时
- 单个 bug 平均系统分析耗时
- 单个 bug 平均节省时间
- 每人每日可处理 bug 数

### 12.2 质量指标

- 相关性判断准确率
- REQ/Epic 关联准确率
- Confluence 文档命中有效率
- GitLab 代码模块定位有效率
- 工时预估偏差
- 报告字段人工修改率

### 12.3 使用指标

- 周活跃用户数
- 人均每日分析 bug 数
- 报告被复制到 Jira 评论的次数
- 报告被采纳比例
- 用户反馈提交率

## 13. MVP 验证方案

### 13.1 验证样本

选取最近 10-20 个真实 QM bug ticket，覆盖以下类型：

- 明确属于本组功能的问题
- 跨模块或跨团队问题
- 需求定义清晰但实现异常的问题
- 需求定义不清导致的问题
- 代码实现与需求不一致的问题
- 测试环境或数据导致的问题

### 13.2 验证方法

对每个 bug ticket 记录：

- 人工分析耗时
- 系统分析耗时
- 系统命中的 REQ/Epic 是否有效
- 系统命中的 Confluence 文档是否有效
- 系统定位的 GitLab 模块是否有效
- 报告哪些字段需要人工修改
- 最终是否采纳系统建议
- 实际节省时间

### 13.3 成功标准

MVP 可继续投入的标准：

- 70% 以上报告达到“可直接使用”或“少量修改后可用”
- 单个 bug 平均节省时间不少于 30 分钟
- 相关性判断准确率达到 80% 以上
- REQ/Epic 关联准确率达到 70% 以上
- GitLab 模块定位有效率达到 60% 以上
- 至少 2 类角色愿意持续使用该报告

## 14. 风险与应对

### 14.1 多源上下文无法准确关联

风险：

- Jira、Confluence 和 GitLab 之间命名不统一，导致检索结果不准确

应对：

- 优先建立模块名、需求编号、接口名、代码目录之间的映射表
- 报告中展示每条上下文的匹配依据
- 允许用户标记上下文是否有效

### 14.2 代码定位置信度低

风险：

- Agent 能找到相关代码，但无法准确判断真实改动点

应对：

- 将代码定位定义为“候选改动范围”，不定义为最终结论
- 强制 RD 确认低置信度代码判断
- 记录 RD 修正后的最终模块，用于后续优化

### 14.3 工时估算被误用

风险：

- 非研发角色直接把系统工时当作承诺工时

应对：

- 工时只输出区间
- 报告中明确标记“需 RD 确认”
- 展示估算依据和不确定因素

### 14.4 范围扩张到通用 Agent 平台

风险：

- 过早建设模板市场、流程编辑器、多 Agent 协作等平台能力，导致 MVP 迟迟无法验证

应对：

- 第一阶段只聚焦 QM bug ticket 分析
- 可配置能力先体现在报告模板和数据源配置
- 等验证效率指标成立后，再抽象为通用工作流能力

## 15. Roadmap

### 15.1 阶段一：个人工作流验证

## 16. 简历与面试表达

### 16.1 项目一句话

设计并实践面向 QM 测试阶段 bug ticket 的 Agent 分析工作流，基于 Jira、Confluence 和 GitLab 多源上下文，自动完成需求关联、代码定位、影响范围分析和工时初评，生成结构化分析报告，提升团队 bug 初筛效率。

### 16.2 可量化表达

个人工作流实测日均处理约 5 个 bug ticket，单个 ticket 节省约 1-2 小时人工分析时间；后续规划为团队内可复用的 B 端提效系统，支持 PO、RD、QA/QM 基于统一报告协作确认问题归属、修复范围和处理建议。

### 16.3 面试重点

可重点讲清：

- 为什么选择 QM bug ticket 分析作为切入场景
- 如何把人工分析流程拆成 Agent 可执行步骤
- 如何关联 Jira、REQ/Epic、Confluence 和 GitLab
- 如何设计结构化报告和人工确认机制
- 为什么 MVP 不先做完整 RBAC 或通用工作流平台
- 后续如何从单场景提效工具抽象到 Agent 工作流编排平台
